# 5. Tracking and Displaying Iteration Commits in Terminal During Phase Pipeline Iterations

Date: 2026-11-04

## Status

Accepted

## Context

Operators running autonomous multi-agent orchestration pipelines via `sandcastle-agy run` or `sc-agy run` monitor progress through visual progress and status banners printed in the host terminal.

Previously, after completing concurrent execution of the Implementer and Reviewer agents in Phase 2 (*Execute + Review*), the orchestrator printed only the count and branch names of modified branches (e.g., `Execution complete. 1 branch(es) with commits:\n  sandcastle/issue-18`). Similarly, after consolidating code changes in Phase 3 (*Merge*), the terminal emitted only a static message (`Branches merged.`).

This lack of detail obscured:
1. Which specific commits were produced on working candidate branches prior to the merge phase.
2. Which code changes were actually consolidated into the Base Branch upon completion of the merge phase.
3. Whether the Base Branch was already up to date when zero new commits landed.

To audit agent output, operators were forced to pause the orchestrator or open a separate terminal window to inspect commit logs with `git log`.

## Decision

1. **Domain Vocabulary Expansion**:
   - Register canonical domain concept `Iteration Commits` in `CONTEXT.md` under *Orquestração e Isolamento*: the set of commits generated by the Implementer and Reviewer agents in candidate branches during an iteration of the Phase Pipeline prior to Merger consolidation.

2. **Dedicated Commit Inspection Seam in Operations Module (`operations.ts`)**:
   - Introduce `GitCommitInfo` data interface representing commit SHA, 7-character short SHA, and subject message.
   - Introduce `getBranchCommits(repoRoot, baseBranch, targetBranch, options)`: queries chronological commits between Base Branch and candidate branch (`baseBranch..targetBranch`) using `git log --reverse --format="%H%x1f%h%x1f%s"`.
   - Introduce `getIntegratedCommits(repoRoot, preMergeHead, postMergeHead, options)`: queries chronological commits integrated between pre-merge and post-merge Base Branch HEAD revisions (`preMergeHead..postMergeHead`).
   - Introduce `getBranchHeadRevision(repoRoot, branchOrRef, options)`: queries branch/ref HEAD revision with `git rev-parse` and fallback to `git rev-parse HEAD`.
   - Introduce formatter functions returning pre-indented arrays of terminal display lines using bullet markers (` • `) and short 7-character hashes:
     - `formatBranchCommitsSummary` / `formatPhase2ExecutionSummary` / `renderPhase2ExecutionSummary` for Phase 2 candidate branch summaries.
     - `formatIntegratedCommitsSummary` / `formatPhase3MergeSummary` / `renderPhase3MergeSummary` for Phase 3 Base Branch merge summaries.
   - Provide zero-throw fault tolerance with graceful fallback to short SHAs with unavailable placeholder when git log queries fail or encounter unexpected errors, ensuring orchestrator execution is never aborted.
   - Injectable `gitRunner` option allowing deterministic unit testing with zero Git dirtying.

3. **Orchestrator Loop Integration (`main.mts`)**:
   - In Phase 2: replace plain branch name listing with `formatPhase2ExecutionSummary` rendering each branch followed by its chronological Iteration Commits (`      • <shortSha> <subject>`).
   - In Phase 3: capture `preMergeHead` revision immediately before merger agent execution, and render `formatPhase3MergeSummary` upon completion under `Branches merged into <baseBranch>.` (or confirm `(no new commits integrated; base branch already up to date)` when revisions match).

4. **Public Interface Re-exports (`cli.ts`)**:
   - Re-export all commit inspection functions, formatters, and type definitions from `cli.ts` for consumers and automated test suites.

## Considered Options

- **Option 1: Raw `git log` stdout dump in orchestrator loop**:
  Directly calling `git log` and piping stdout inside `main.mts`. Rejected because raw git log output contains terminal escape sequences, inconsistent pagination, lacks structured indentation, and unhandled errors could crash the orchestrator process.
- **Option 2: Relying solely on `sandbox.run()` commit metadata**:
  Using the commits array returned by the Sandcastle sandbox runner. Rejected because `sandbox.run()` only reports commits created within an individual container run, making it impossible to capture cross-agent multi-step workflows (Implementer + Reviewer), merge commits, or verify final landing on the host Base Branch without querying the Target Repository boundary.
- **Option 3: Dedicated domain inspection seam in operations module with mockable Git runner and resilient formatters (chosen)**:
  Decouples Git command execution and output formatting from the orchestration loop, guarantees chronological ordering, ensures zero-throw fault tolerance, and enables deterministic unit testing with zero filesystem mutations.

## Consequences

- **Complete Operator Visibility**: Operators immediately see all Implementer and Reviewer commits before merge, and confirmed integrated commits post-merge without leaving the terminal.
- **Pipeline Resilience**: Git query failures or missing commit data fall back gracefully without interrupting the multi-agent pipeline.
- **Zero Behavioral Divergence**: Identical commit visualization and formatting across both canonical `sandcastle-agy` and shorthand `sc-agy` commands.
- **Deterministic Testability**: 100% test coverage using in-memory mock Git runners with zero git dirtying.
- **Clean Plain-Text Logs**: Indented terminal output formatted with unicode bullet markers without ANSI color codes, ensuring compatibility with standard log parsers and redirection.
